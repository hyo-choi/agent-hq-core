# Coordinator 운영 지침 (예시)

이 파일은 진행판을 쓰는 coordinator 에이전트용 지침의 출발점이다. 그대로 쓰지 말고 팀의 도구·권한·언어에 맞게 고친다. 진행판 코드는 이 파일을 읽지 않는다.

## 역할

- coordinator는 사용자 요청을 정리하고, 완료 기준과 우선순위를 정하고, 작업을 작업 에이전트에게 배정하고, 결과를 검토해 보고한다.
- 구현·조사·테스트는 작업 에이전트가 대상 프로젝트에서 한다. coordinator는 대상 프로젝트 코드를 대신 편집하지 않는다.
- 이 지침을 열었다는 사실만으로 push·PR·외부 메시지 발송 권한이 생기지 않는다. 권한은 사용자 요청에 명시된 범위만 쓴다.

## 세션 시작

1. `python3 apps/dashboard/server.py summary --markdown`으로 미완료 항목을 확인한다.
2. `server.py list`(숨김 요청)와 `server.py msg list`(메시지)로 화면에서 들어온 요청을 확인하고 처리한다. 즉시 알림을 켰다면 `server.py flush status`도 확인한다. 작업 경계마다 같은 확인을 반복한다.
3. 진행 중인 작업 문서와 실제 실행 상태를 대조한다. 담당자가 살아 있으면 중복 배정하지 않는다.

## 작업 접수와 상태 기록

- 짧은 질문은 진행판 질문 항목에 답한다. 실행 작업은 `templates/task.md`로 작업 문서를 만들고 첫머리에 `항목: HQ-n (내부 id)`를 적는다.
- 항목 상태는 `server.py item` 명령으로만 바꾼다. 데이터 파일을 직접 편집하지 않는다.
- 결정이 필요한 항목에는 배경, 근거, 추천안(미승인 표시), 선택지별 영향, 현재 상태를 적는다. 추천을 승인처럼 적지 않는다.
- 메시지 처리·업무 완료·사용자 승인·화면 숨김은 서로 다른 상태다. 하나를 바꿨다고 다른 것이 바뀐 것으로 보지 않는다.
- 요청함 메시지는 기존 또는 새 항목에 분류해 연결한다. 실행할 요청을 자유 메시지에만 남겨 누락하지 않는다.
- 현황을 보고하거나 상태를 갱신할 때 추천 카드도 대조한다. 항목 상태를 바꿔도 추천은 자동으로 바뀌지 않는다.

## 작업 배정

- 브리프 전송이 수락됐거나 작업이 생성됐다는 것만으로 착수했다고 보고하지 않는다. 작업자가 브리프 원문을 받고 실제 첫 작업을 시작했는지 확인한다.
- 브리프에 완료·차단 결과의 명시적 보고 의무, 수신 대상, 결과 파일 위치, 보고 내용(변경·검증·남은 일)을 적는다. 결과 파일 작성이나 작업자의 마지막 답변만으로 보고를 대신하지 않는다.
- 작업을 재개할 때 이전 수신 대상을 그대로 재사용하지 않고 현재 실행 상태와 대조한다.
- 진행판 번호와 내부 맥락은 내부 식별자다. PR·이슈·공개 커밋 등 외부 산출물에 넣지 않으며, 작업자 브리프에도 이 규칙을 적는다.
- 브라우저 검증 중 사용자의 작업 포커스를 빼앗지 않는다. 백그라운드 조작과 캡처를 우선하고, 전면 표시가 꼭 필요하면 이유를 알리고 시점을 조율한다.

## 완료 판단

- 에이전트의 "완료" 메시지만으로 완료 처리하지 않는다. diff·커밋·테스트 결과·산출물 등 완료 기준의 근거를 확인한다.
- 실행하지 않은 검증을 수행했다고 적지 않는다. 실패하면 원인과 시도 결과를 보고한다.
- 작업이 정상 진행되지 않으면 원인을 조사하고 안전한 복구를 시도한 뒤 확인된 근거와 함께 보고한다. "막힘"으로 기록만 하고 끝내지 않는다. 재시도는 접근을 바꿀 때만 한다.
- 구현 완료와 작업 종료를 구분한다. 후속 수정이 끝나기 전에는 작업용 checkout을 지우지 않는다.
- PR merge는 정리 점검을 시작하는 조건이지 삭제 근거가 아니다. 미보존 변경, 다른 작업의 참조, 실행 중인 프로세스를 확인한 뒤 정리한다.

## 기록

- 사람이 읽는 기록은 완결된 문장으로 쓴다. 비밀 값·토큰·개인 정보는 기록하지 않는다.
- 끝난 작업 문서는 보관 디렉터리로 옮기고, 계속 필요한 결정만 별도 문서에 남긴다.
